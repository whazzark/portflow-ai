## Summary

Let an authorized administrator archive one eligible warehouse or a selection of them in one action.
Archiving a warehouse **cascades to its available doors** in the same transaction, with the same
archive time, actor, and comment. A warehouse is ineligible when it is already archived or when any
of its doors is currently in use by a Planned or Active Discharge.

Five sibling archive slices are already delivered (`GH-195`, `GH-220`, `GH-225`, `GH-200`, `GH-205`).
Their API shape — single `POST /:id/archive` plus bulk `POST /archive`, partial success, one stable
reason per blocked record, `forUpdate()` row locks, an affected-rows guard for all-or-nothing — is
transposed here rather than reinvented. The work concentrates on **five** things:

1. **A warehouse lifecycle slice that does not exist yet.** `apps/api/app/warehouses/` currently
   holds only `list/`. There is no archive use case, no policy method beyond `list`, no validator,
   no exceptions, no repository mutation, and no route. All of it is new, modelled on
   `app/weighing_areas/`.

2. **The door cascade** — the one genuinely new mechanism in this slice. Warehouse eligibility is
   derived from *door* usage through the existing `WAREHOUSE_DOOR` checker (research **D1**), and a
   successful archival updates two tables inside one transaction under a fixed lock order
   (research **D3**).

3. **A migration recording *why* each door was archived.** FR-013 requires distinguishing a door
   archived by its warehouse's cascade from one archived on its own, so Reactivate a Warehouse
   (`#211`) can restore exactly the cascaded set. `warehouse_doors` gains
   `archived_with_warehouse` (research **D2**).

4. **Exposing lifecycle context that the read contract currently drops.** `WarehouseTransformer`
   returns only `id`/`name`/`status`/`footprint`/`doors{id,name,status,lat,lng}` — no `archivedAt`,
   no actor, no comment, on the warehouse or on its doors. US1 scenario 5 and FR-013 need all of it
   (research **D8**).

5. **Generalizing the delivered bulk-selection interaction from point markers to polygons.**
   `#200`/`#205` delivered select mode, checkable markers, the bulk action bar, and the
   Ctrl/Cmd+A / Escape shortcuts on the Checkpoints map. FR-045 requires warehouses to meet that
   same model, not a second one — so the kind-agnostic parts move into `components/resource-map/`
   and Checkpoints keeps its wording byte-identical through a thin wrapper (research **D5**, **D6**,
   **D7**).

## Technical Context

**Language/Version**: TypeScript 5.x on Node.js 25

**Primary Dependencies**: API — AdonisJS 7, Lucid ORM 22, VineJS, Bouncer, Tuyau. Web — React 19,
TanStack Start/Router/Query, shadcn/ui, Tailwind 4, MapLibre (`maplibre-gl`) polygon layers.

**Storage**: PostgreSQL 17. `warehouses` already carries `status`, `archived_at`,
`archived_by_user_id`, `archive_comment`, and the reactivation columns; so does `warehouse_doors`.
**One migration is still required** for `warehouse_doors.archived_with_warehouse` (FR-013).
`apps/api/database/schema.ts` is generated by `node ace migration:run` and must be regenerated.

**Testing**: Japa (API unit + integration), Vitest + Testing Library + MSW (web), Playwright for
browser flows.

**Target Platform**: Web application (single operating site, session-cookie auth).

**Performance Goals**: A 50-warehouse / 500-door submission resolves within 2s (SC-011). Door usage
is assessed set-based over all candidate door ids in one query, never one query per warehouse
(inherited from `#240` FR-012).

**Constraints**: Partial success with exactly one reason per blocked warehouse; all-or-nothing
persistence spanning **two tables**; eligibility assessed at submission time under row locks taken
in a fixed order so concurrent submissions archive each warehouse and each door exactly once.

**Scale/Scope**: Up to 200 warehouses per site (`#207` SC-002); no cap on selection size.

**Principle VI required action.** `CONTEXT.md:152` says a warehouse "cannot be archived while it
still has available warehouse doors". The product decision recorded in the spec's Clarifications
replaces that rule with the cascade. Leaving both statements standing would duplicate a canonical
decision in two places, which Principle VI forbids. **Amending the `Warehouse` entry in `CONTEXT.md`
is therefore part of this delivery, not a follow-up** (research **D10**, task-level obligation).
This is a documentation correction that keeps the single home authoritative, not a constitution
violation.

Two boundary nuances are inherited rather than introduced:

- **The bulk in-use check runs inside the repository transaction**, as the delivered dock, truck,
  and weighing-area slices all do, because eligibility must be assessed atomically with the row
  locks it guards. The single path keeps its check in the use case. Research **D3** records why this
  asymmetry is inherited rather than "fixed" here.
- **The cascade write lives in the repository**, not the use case. The use case decides *whether* to
  archive; the repository owns the fact that "archive this warehouse" means two conditional writes
  under one transaction. That is exactly the split `apps/api/AGENTS.md` prescribes ("Repositories
  expose domain-oriented operations and own locks, transactions, and conditional writes").

**Design risks carried into `/speckit-tasks`**, in descending order:

1. **The two extractions touch delivered code** (**D5**, **D7**). They are the only tasks that can
   regress features already in production. Sequence them first, behind their existing test suites,
   and keep them behavior-preserving — no wording or markup changes while extracting.
2. **The migration gates everything on the API side** (**D2**). `schema.ts` regeneration must happen
   before the model, repository, or transformer reference `archivedWithWarehouse`.
3. **Route ordering** — `/warehouses/archive` must be declared before `/warehouses/:id/archive`,
   or the bulk route resolves as `:id = 'archive'`. Cheap to get wrong, cheap to test.
4. **Hand-written MSW fixtures** do not follow the Tuyau contract regeneration (**D8**) and must be
   widened manually, or the web suites fail on missing lifecycle fields.
