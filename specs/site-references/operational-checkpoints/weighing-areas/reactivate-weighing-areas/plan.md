## Summary

Let an authorized administrator reactivate one archived weighing area, or a selection of archived
weighing areas together, from the existing Checkpoints consultation map (`/checkpoints`).

Research into the current codebase found the **most complete baseline any lifecycle slice has
started from**, because the two slices either side of this one deliberately left the seams open.

On the **backend**, the individual reactivate path already exists end to end and is correct:
`POST /api/v1/weighing-areas/:id/reactivate`, `ReactivateWeighingAreaUseCase`,
`WeighingAreaPolicy.reactivate`, `LucidWeighingAreaRepository.reactivateArchived` (a status-guarded
`UPDATE` that re-reads to distinguish `NOT_FOUND` from `ALREADY_AVAILABLE`), and
`WeighingAreaAlreadyAvailableException`. It is covered at use-case level and by one happy-path HTTP
case. Exactly **one production defect** stands against the spec: `reactivateWeighingAreaValidator`
is `vine.string().nullable().optional()` where every sibling lifecycle validator uses the shared
`lifecycleComment()` — so an over-long reactivation comment is accepted and an untrimmed one is
stored (spec FR-007, FR-008). That one-line alignment is the only change to shipped backend
behavior in this slice.

The **bulk backend does not exist** and needs no new abstraction. `findBulkBlockers(ids, byId,
expectedStatus, usedIds?)` in `weighing_area_lifecycle_blockers.ts` already accepts
`expectedStatus: 'ARCHIVED'`, already emits `ALREADY_AVAILABLE`, and already skips the usage check
on that branch; `BulkWeighingAreaLifecycleBlocker` already declares the reason;
`BulkWeighingAreaLifecycleResult`, `lifecycleIds()`, and `lifecycleComment()` are all in place. So
the bulk surface is five mechanical additions mirroring `archiveAvailableMany` minus its usage
lookup, and mirroring `LucidDockRepository.reactivateArchivedMany` exactly.

On the **frontend**, #205 generalized the whole map select mode to be kind-and-intent-driven rather
than dock-specific: the page computes `checkableIds` from a `BULK_LIFECYCLE_INTENTS` table, the
toolbar is the resource-agnostic `BulkCheckpointLifecycleActions` taking an `intent` prop and a
`submit` callback, and both checkpoint kinds already route through `toBulkLifecycleOutcome`
adapters. It then left three explicit `#206` placeholders: `BULK_LIFECYCLE_INTENTS.WEIGHING_AREA`
is `['ARCHIVE']`, `BULK_LIFECYCLE_DESCRIPTIONS.WEIGHING_AREA` has no `REACTIVATE` entry, and
`submitBulkLifecycle` short-circuits every weighing-area selection to `archiveMany`. **Filling
those three placeholders is the entire bulk frontend change** — no component is renamed, no prop is
added, no rule moves, and `checkpoint-map.tsx` and its test mock are untouched.

The individual frontend path is the same frontend-only gap #201 found for docks:
`use-weighing-area-mutations.ts` has no `reactivate` mutation, and `weighing-area-details.tsx`
renders its footer only `when area.status === 'AVAILABLE'`, so an archived weighing area's sheet
offers no action at all. `weighing-area-lifecycle-actions.tsx` gains the archived branch that
`dock-lifecycle-actions.tsx` already has — keeping the weighing-area component's own better error
handling (field-level validation detail, dialog stays open on refusal), which the dock component
lacks and which spec US3 scenario 3 requires.

## Technical Context

**Language/Version**: TypeScript (apps/web: React 19 via TanStack Start; apps/api: AdonisJS on
Node.js)

**Primary Dependencies**: TanStack Router/Query (`useWeighingAreaMutations`, `tuyauQuery`),
`@tuyau/react-query` (typed client; the committed registry under `apps/api/.adonisjs/client/` is
regenerated by the `generateRegistry` hook in `adonisrc.ts` and must pick up the new
`weighing_areas.reactivate_many` route name), `sonner`; Radix-based `AlertDialog`/`Field`
primitives (already used by `weighing-area-lifecycle-actions.tsx` and
`bulk-checkpoint-lifecycle-actions.tsx`); backend: AdonisJS, VineJS, Lucid, Bouncer, Luxon (all
pre-existing; the bulk backend follows the Dock bulk-reactivate shape verbatim)

**Storage**: PostgreSQL via the existing `weighing_areas` table — no migration, no schema change.
The archive and reactivation contexts are separate column groups (`archived_at`/
`archived_by_user_id`/`archive_comment` and `reactivated_at`/`reactivated_by_user_id`/
`reactivation_comment`), so preserving archive context (spec FR-010) is a property of the schema,
not something the code must arrange. Bulk reactivation uses `SELECT … FOR UPDATE` inside one
transaction, exactly as `archiveAvailableMany` and `LucidDockRepository.reactivateArchivedMany` do.

**Testing**: Vitest + Testing Library + MSW for `apps/web`; Japa for `apps/api` — new integration
spec `apps/api/tests/integration/weighing_areas/lifecycle/bulk/reactivate.spec.ts` and unit spec
`apps/api/tests/unit/weighing_areas/lifecycle/bulk_reactivate.spec.ts` alongside their `archive`
counterparts, plus individual-reactivate HTTP cases added to the existing
`apps/api/tests/integration/weighing_areas.spec.ts`; new component tests under
`apps/web/src/features/weighing-areas/__tests__/reactivate/` and
`apps/web/src/features/checkpoints/__tests__/bulk-reactivate-weighing-areas/`

**Target Platform**: Web application (desktop and tablet browsers)

**Project Type**: Web application monorepo (`apps/api` + `apps/web`), extending an existing feature
area

**Performance Goals**: Available status visible in consultation within 2 seconds of a successful
submission (SC-001); a 100-identifier bulk reactivation completes within 2 seconds in the
acceptance environment (SC-011), matching the row-locked bulk `UPDATE … WHERE id IN (…)` shape
already proven at that scale for weighing-area archiving and dock reactivation

**Constraints**: Must reuse the existing `/checkpoints` route and its `selecting=weighing-areas`
mode rather than introducing a second select mode, a second map control, or a separate
weighing-area page; must not change the `checkpoint=<kind>:<id>` single-selection contract, the
`BulkCheckpointLifecycleActions` public props, or the `CheckpointMap`/`mock-checkpoint-map`
`checkableIds` contract; must not regress the bulk-archive behavior #205 shipped or the
bulk-reactivate behavior #201 shipped — every existing test under
`apps/web/src/features/checkpoints/__tests__/bulk-archive/` and `.../bulk-reactivate/` must keep
passing unchanged; bulk reactivation stays scoped to Weighing Area (no other site reference gains
it here)

**Scale/Scope**: One new bulk API surface (route, validator, use case, repository method,
controller method) sized identically to the existing weighing-area bulk-archive surface; one
one-line validator correction; three table/branch entries on an already-generalized frontend; two
individual-path UI wirings; no new persisted entity, no data migration, no new search param, no new
component

**Structure Decision**: Web application monorepo, already in place. The individual-reactivate
backend is reused verbatim apart from its validator; the bulk backend copies the shape #205
delivered for archiving and #201 delivered for dock reactivation, in the same directories, so there
is no discovery risk. On the frontend, weighing-area-specific lifecycle work stays in
`apps/web/src/features/weighing-areas`, and the map-selection work is confined to two table entries
and one branch in `apps/web/src/features/checkpoints`. No new route, no new search param, no new map
control, no new component.

**Why this slice adds no abstraction**: #201 generalized the dock-only select mode into the
kind-and-intent model, and #205 extended that model to weighing areas for the archive direction and
recorded the reactivate direction as this issue's to fill. The seam is already the right shape, and
the work is to use it. The only design question left open — whether a bulk reactivation should keep
blocked entries checked for retry — is settled by reusing #201's answer verbatim
(`handleBulkReactivateSuccess` clears the whole selection, because neither reactivation blocker
becomes eligible on a retry), which the page already applies to any `REACTIVATE` intent regardless
of kind. See research decision D5.
