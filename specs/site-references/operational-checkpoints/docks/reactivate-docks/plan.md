## Summary

Let an authorized administrator reactivate one archived dock, or a selection of archived docks
together, from the existing checkpoint consultation map (`/checkpoints`).

Research into the current codebase found the same **split baseline** #200 found for archiving, one
step further along. The individual reactivate backend
(`POST /api/v1/docks/:id/reactivate`, `reactivateDockValidator`, `ReactivateDockUseCase`,
`DockPolicy.reactivate`, `LucidDockRepository.reactivateArchived`,
`DockAlreadyAvailableException`) already exists, was delivered under #178, and is covered at the
use-case level (eligible, `NOT_FOUND`, `ALREADY_AVAILABLE`) plus two HTTP-level tests. **No
production backend change is needed for the individual path.** But **no frontend ever calls it**:
`use-dock-mutations.ts` has no `reactivate` mutation, and `dock-details.tsx` renders its footer
only `when dock.status === 'AVAILABLE'`, so an archived dock's sheet has no action at all. The
individual user story is a **frontend-only gap**.

The multiple-reactivate user story **does not exist at any layer**. Everything it needs is already
shaped by the two slices around it: Customers ship `POST /customers/reactivate`,
`ReactivateCustomersUseCase`, and `LucidCustomerRepository.reactivateArchivedMany`; and #200 left
Dock's own bulk machinery reactivation-ready — `findBulkBlockers(ids, docksById, expectedStatus,
usedIds?)` already accepts `expectedStatus: 'ARCHIVED'` and already emits `ALREADY_AVAILABLE`,
`BulkDockLifecycleBlocker` already declares that reason, and `lifecycleIds`/`lifecycleComment`
already live in the shared validator module. This plan therefore adds **no new helper and no new
shared abstraction** on the backend: one use case, one validator, one repository method, one
controller method, one route.

The real design work is in the **map's select mode**, which #200 hard-coded to `AVAILABLE` in three
places (`checkpoints-page.tsx`'s `toggleDockChecked`, its Ctrl/Cmd+A handler, and
`checkpoint-map.tsx`'s `isAvailableDock`/`isSelectableDock`, duplicated again in the test mock).
Rather than add a second select mode and a second map control for the reverse direction, this plan
makes the existing `selecting=docks` mode **status-aware and homogeneous**: any dock is checkable
while nothing is checked, and the first check fixes the selection's *intent* (`AVAILABLE` →
Archive, `ARCHIVED` → Reactivate) so docks of the other status stop being checkable until the
selection is cleared. The eligibility rule moves out of the map component into the page, which
passes down a `checkableDockIds` set — removing the duplicated status rule from both the real map
and its test mock. `BulkArchiveDocksActions` becomes `BulkDockLifecycleActions` with an `intent`
prop, the direct counterpart of `bulk-lifecycle-actions.tsx`'s `isArchived`, and
`DockLifecycleActions` gains the archived branch that `customers/ui/lifecycle-actions.tsx` already
has — the extension #200's research (D6) explicitly deferred to this issue.

## Technical Context

**Language/Version**: TypeScript (apps/web: React 19 via TanStack Start; apps/api: AdonisJS on
Node.js)

**Primary Dependencies**: TanStack Router/Query (`useDockMutations`, `tuyauQuery`),
`@tuyau/react-query` (typed client; the committed registry under `apps/api/.adonisjs/client/` is
regenerated by the `generateRegistry` hook in `adonisrc.ts` and must pick up the new
`docks.reactivate_many` route name), `sonner`; Radix-based `AlertDialog`/`Field` primitives
(already used by `dock-lifecycle-actions.tsx` and `bulk-archive-docks-actions.tsx`); backend:
AdonisJS, VineJS, Lucid, Bouncer, Luxon (all pre-existing; individual-reactivate backend files are
read-only references, bulk backend files are new following the Customer bulk-reactivate shape)

**Storage**: PostgreSQL via the existing `docks` table — no migration, no schema change. Bulk
reactivation uses `SELECT … FOR UPDATE` inside one transaction, exactly as
`LucidCustomerRepository.reactivateArchivedMany` and `LucidDockRepository.archiveAvailableMany` do.

**Testing**: Vitest + Testing Library + MSW for `apps/web`; Japa for `apps/api` — new integration
spec `apps/api/tests/integration/docks/lifecycle/bulk/reactivate.spec.ts` and unit spec
`apps/api/tests/unit/docks/lifecycle/bulk_reactivate.spec.ts` alongside their `archive`
counterparts, plus individual-reactivate HTTP cases added to the existing
`apps/api/tests/integration/docks.spec.ts`; new component tests under
`apps/web/src/features/docks/__tests__/reactivate/` and
`apps/web/src/features/checkpoints/__tests__/bulk-reactivate/`

**Target Platform**: Web application (desktop and tablet browsers)

**Project Type**: Web application monorepo (`apps/api` + `apps/web`), extending an existing feature
area

**Performance Goals**: Available status visible in consultation within 2 seconds of a successful
save (SC-001); a 100-identifier bulk reactivation completes within 5 seconds in the acceptance
environment (SC-010), matching the row-locked bulk `UPDATE … WHERE id IN (…)` shape already proven
for customers and for dock archiving at that scale

**Constraints**: Must reuse the existing `/checkpoints` route and its `selecting=docks` mode rather
than introducing a second select mode, a second map control, or a second dock surface; must not
change the `checkpoint=<kind>:<id>` single-selection contract or the resource-agnostic
`resource-map-*` primitives' public surface; must not modify the individual-reactivate production
backend files, which are already correct and already tested; must not regress the bulk-archive
behavior #200 just shipped — every existing test under
`apps/web/src/features/checkpoints/__tests__/bulk-archive/` must keep passing unchanged; bulk
reactivation stays scoped to Dock (no bulk reactivate for weighing areas or any other site
reference)

**Scale/Scope**: One new bulk API surface (route, validator, use case, repository method,
controller method) sized identically to the existing Dock bulk-archive surface; two existing UI
components generalized from one-directional to bidirectional; one eligibility rule relocated from
the map to the page; no new persisted entity, no data migration, no new search param

**Structure Decision**: Web application monorepo, already in place. The individual-reactivate
backend is reused verbatim; the bulk backend copies the shape #200 delivered for archiving, in the
same directories, so there is no discovery risk. On the frontend, dock-specific lifecycle work
stays in `apps/web/src/features/docks`, and the map-selection work stays in
`apps/web/src/features/checkpoints`, both extended in place rather than duplicated for the reverse
direction. No new route, no new search param, no new map control.

**Why generalize rather than duplicate**: #200's research recorded (D6) that `DockLifecycleActions`
and `BulkArchiveDocksActions` were deliberately archive-only, and explicitly left this issue the
choice between extending them to branch like the Customer components or adding reactivate-only
siblings. Extending wins: the two directions differ in a label, a dialog sentence, a mutation, and
a toast — the same delta `customers/ui/lifecycle-actions.tsx` and `bulk-lifecycle-actions.tsx`
already absorb with one boolean. A reactivate-only sibling would copy the ~140-line bar (selection
count, blocked-reason list, comment field, toolbar chrome, dialog) to change four strings, and the
two copies would drift the first time the toolbar changes.
