# Quickstart: Validate Updating a Transport Company

## Prerequisites

- Node.js compatible with the repository toolchain
- PNPM 10.28.1
- Repository dependencies installed with `pnpm install`
- API and web environment files configured from their checked-in examples
- PostgreSQL available for the manual browser flow; automated API tests use in-memory SQLite

## 1. Apply the new constraint and prepare the dataset

```bash
pnpm --filter @portflow/api db:fresh
```

This runs the new `transport_companies_name_unique` migration and re-seeds the fixtures. Confirm the command succeeds: the seeder already refuses case-insensitively colliding fixture names, so a failure here means fixture data drifted and must be fixed before the index can be trusted.

`apps/api/database/schema.ts` is regenerated by the migration run. Do not edit it by hand; commit whatever the generator produces.

Authoritative field rules and the write boundary are defined in [data-model.md](./data-model.md); request and response shapes are defined in [contracts/http-api.md](./contracts/http-api.md).

## 2. Run focused API verification

```bash
pnpm --filter @portflow/api test unit \
  --files=tests/unit/transport_companies/administration/update.spec.ts
pnpm --filter @portflow/api test integration \
  --files=tests/integration/transport_companies/administration/update.spec.ts
```

Expected outcomes:

- An unauthenticated request is refused with `401` and changes nothing.
- An active observer is refused with `403` and changes nothing.
- Both administration roles rename an available company and receive the complete updated record.
- The response preserves `id`, `status`, `createdAt`, and every archive and reactivation field.
- A name with surrounding whitespace is stored trimmed.
- A blank name, a whitespace-only name, a missing `name`, and a 256-character name are each refused with `422`, and the stored name is unchanged.
- A 255-character name is accepted.
- A name already used by another company is refused with `409 E_TRANSPORT_COMPANY_NAME_CONFLICT`, including when it differs only by letter case or surrounding whitespace, and neither company changes.
- Resubmitting a company's own current name succeeds and is not reported as a duplicate.
- Updating an archived company is refused with `409 E_TRANSPORT_COMPANY_ARCHIVED`.
- Updating an unknown id is refused with `404 E_TRANSPORT_COMPANY_NOT_FOUND`.
- Trucks attached to the renamed company keep their association.

## 3. Run focused web verification

```bash
pnpm --dir apps/web exec vitest run src/features/transport-companies
```

Expected outcomes:

- **Edit company** appears only for an administrator viewing an available company.
- An observer sees no update affordance, and `?companyMode=edit` does not open a form for them.
- An administrator viewing an archived company sees no update affordance.
- The edit form opens in the detail pane, pre-filled with the current name, without leaving the directory.
- A successful save shows a confirmation, returns to the details view, and the renamed company is reflected in the directory and its details.
- A `422` response attaches a message to the name field; a `409` duplicate and a `409` archived response surface as distinct error feedback.
- After a refusal the administrator can correct the value and resubmit without reopening the company.
- Cancelling leaves the company unchanged and returns to the details view.
- The existing consultation tests still pass: lifecycle tabs, counts, search, ordering, details, empty, and retry behavior are unaffected.

## 4. Run repository verification

```bash
pnpm check
pnpm typecheck
pnpm test
```

All commands must pass before the PR is marked ready. Because no Playwright suite is configured, also complete the affected browser flow below.

## 5. Exercise the affected browser flow

```bash
pnpm dev
```

Validate in a desktop viewport and a narrow mobile viewport:

1. Sign in as an operations administrator and open **Site references → Transport resources**.
2. Select an available company, confirm **Edit company** is offered, and open it. Confirm the form is pre-filled with the current name and the URL carries `companyMode=edit`.
3. Reload the page in edit mode and confirm the form is restored from the URL.
4. Save a new name. Confirm the confirmation appears, the panel returns to details, and the directory list shows the new name in its correct alphabetical position.
5. Confirm the company's stable identity, status, and archive or reactivation context are unchanged, and that **Last updated** has advanced.
6. Submit a blank name and a name copied from another company, including one differing only by letter case. Confirm each refusal is distinct and the company is unchanged.
7. Correct the value in place and resubmit; confirm it succeeds without reopening the company.
8. Submit a name with leading and trailing spaces and confirm the stored value is trimmed.
9. Resubmit the company's current name and confirm it succeeds without a duplicate error.
10. Open an archived company and confirm no update affordance is offered; then request `?companyMode=edit` for it directly and confirm no form opens.
11. Confirm a truck attached to the renamed company still shows it, now under the new name.
12. Sign in as an observer and confirm the company is readable with no update affordance anywhere.

Finally, repeat the API access check with an unauthenticated session and a non-active user; both must be refused before any company is modified.
