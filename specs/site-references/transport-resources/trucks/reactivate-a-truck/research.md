# Research: Reactivate a Truck

All Technical Context items are resolved from the existing codebase; no NEEDS CLARIFICATION items remain.

## Decision: Mirror the Archive a Truck slice shape in a `reactivate/` directory

**Decision**: Add `apps/api/app/trucks/reactivate/reactivate_truck_use_case.ts` and `reactivate_trucks_use_case.ts` beside the existing `archive/` directory, following the exact shape merged for `#225`: the use case builds a command, delegates to a repository method that performs every check inside one transaction, and maps the returned discriminated result to domain exceptions. `apps/api/app/customers/reactivate/` and `apps/api/app/docks/reactivate/` already use this directory name for the same transition.

**Rationale**: `TruckPolicy`, `TruckTransformer`, the `Truck` model, the `trucks` table with its full reactivation columns, the lifecycle validators, and the bulk result envelope all already exist. Only the reverse write path is missing. Mirroring an already-reviewed, already-tested pattern keeps deep-boundary ownership consistent with Constitution Principle V and makes this slice reviewable as a diff against a known shape.

**Alternatives considered**: A single `lifecycle/` directory holding both directions — rejected because `customers` and `docks` both establish `archive/` and `reactivate/` as sibling directories, and renaming the merged `archive/` directory would churn `#225`'s tests for no behavioral gain. A generic site-reference lifecycle service — rejected for the same reasons the List Trucks, Create a Truck, and Archive a Truck plans rejected it: each resource carries a different eligibility rule, and this slice proves the point, since the truck rule (available transport company) has no customer or dock counterpart.

## Decision: Refuse reactivation under an archived transport company

**Decision**: An archived truck may be reactivated only when its current `transportCompanyId` references a company whose `status` is `AVAILABLE`. Otherwise the reactivation is refused with a dedicated conflict and the truck stays archived. The refusal names the two remedies, both owned by other slices: reactivate the company, or reassign the truck through Update a Truck (`#224`).

**Rationale**: This is derived from a recorded invariant, not invented for this slice. `CONTEXT.md` defines a transport company as one that "cannot be archived while it still provides available trucks", `LucidTransportCompanyRepository#archiveAvailable` enforces exactly that by refusing with `HAS_AVAILABLE_TRUCKS`, and both `CreateTruckUseCase` and `UpdateTruckUseCase` already refuse an unavailable company through `InvalidTransportCompanyException`. Without this gate, reactivation would be the one path in the system able to produce an available truck under an archived provider — a state the company-archival rule is specifically designed to prevent, and one that would surface the archived company as the provider of a truck offered for new operational work.

**Known consequence — the escape hatch does not exist yet**: neither remedy the refusal points at is currently implemented. Reactivate a Transport Company (`#221`) is still in the backlog — `apps/api/app/transport_companies/` has no reactivate use case, route, or policy method — and Update a Truck (`#224`) cannot reassign an *archived* truck's provider, because `UpdateTruckUseCase` refuses one with `ArchivedTruckReadOnlyException`. Archive a Transport Company (`#220`, FR-004) deliberately lets a company be archived while it still provides archived trucks, so this state is reachable today: archive a truck, then archive its company, and the truck cannot return to service until `#221` ships.

This does not change the design — reactivating under an archived provider would break a live invariant, and no alternative in this slice can fix that — but it is a real product consequence the reviewer should decide about, and it is why the refusal message names both remedies rather than only the reassignment one. The options, all outside this slice: accept it and prioritize `#221`; or widen `#224` to allow provider reassignment on archived trucks. Neither is assumed here.

**Alternatives considered**: Allowing reactivation and cascading the company back to available — rejected outright: this slice must not change any transport company's lifecycle state (FR-021), and silently reactivating a provider the site deliberately retired would be a far larger, unrequested decision. Allowing reactivation and leaving the inconsistency for someone else to notice — rejected because it breaks a rule the company-archival path actively enforces, so the two features would disagree about the same invariant. Requiring the administrator to pick a new company as part of the reactivation payload — rejected as smuggling Update a Truck's provider-reassignment behavior (`#224`) into this slice, and as making the reactivation payload diverge from every other lifecycle payload in the codebase.

## Decision: Enforce the company gate under a `FOR UPDATE` lock on the company row

**Decision**: `LucidTruckRepository#reactivateArchived` runs in one transaction that (1) loads the truck `forUpdate`, (2) returns `NOT_FOUND` / `ALREADY_AVAILABLE` from that row, (3) loads that truck's `TransportCompany` row `forUpdate` and returns `TRANSPORT_COMPANY_ARCHIVED` unless it is `AVAILABLE`, (4) issues the status-guarded `UPDATE ... WHERE id = ? AND status = 'ARCHIVED'`, and (5) reloads the truck with `preload('archivedBy')` and `preload('reactivatedBy')`.

**Rationale**: A plain read of the company status would leave a check-then-act window: a company archival committing between the read and the write would produce exactly the state the invariant forbids. Locking the company row closes it, and it is the discipline this codebase already uses for the same invariant in the other direction — `LucidTruckRepository#create` locks the company row before inserting an available truck, and `LucidTransportCompanyRepository#archiveAvailable` locks that same row before counting available trucks, each with a comment explaining why. Whichever transaction takes the lock first commits before the other observes the state: if the company archival wins, this reactivation reads `ARCHIVED` and refuses; if the reactivation wins, the company archival sees the newly available truck and refuses with `HAS_AVAILABLE_TRUCKS`. Reading the company *after* taking the truck lock is safe because an archived truck cannot be reassigned — `updateAvailable` is guarded by `WHERE status = 'AVAILABLE'` and `UpdateTruckUseCase` refuses an archived truck outright — so the `transportCompanyId` read under the truck lock is authoritative for the duration of the transaction.

**Deadlock analysis**: This path acquires truck locks before company locks, the opposite order from `create`. No cycle is possible: `create` waits on a company lock and then *inserts* a new truck row, never waiting on an existing truck lock, and both company-archival paths take company locks and then perform unlocked reads of `trucks`. The only path that holds truck locks and then waits for a company lock is this one.

**Alternatives considered**: Validating company availability in the use case through `TransportCompanyRepository#findById` before delegating, as `UpdateTruckUseCase` does for reassignment — rejected because `findById` performs no lock, so the check-then-act window would remain; `UpdateTruckUseCase` tolerates it only because its write is additionally pinned by `expectedTransportCompanyId`, a compare-and-swap this transition has no equivalent for. A `SELECT ... FOR SHARE` on the company — rejected because the company-archival path takes an exclusive lock on the same row, so a shared lock would not serialize the two. A database-level constraint or trigger enforcing the invariant — rejected as introducing a new enforcement mechanism outside the layering the constitution establishes, for a rule two application paths already own.

## Decision: Two new truck exceptions, both `409`

**Decision**: Add `TruckAlreadyAvailableException` (`409`, `E_TRUCK_ALREADY_AVAILABLE`, "Truck is already available") and `TruckTransportCompanyArchivedException` (`409`, `E_TRUCK_TRANSPORT_COMPANY_ARCHIVED`, "Truck transport company is archived; reactivate the company or reassign the truck before returning it to service") to `truck_exceptions.ts`. `TruckNotFoundException` (`404`) is reused unchanged from `#225`.

**Rationale**: `TruckAlreadyAvailableException` mirrors `CustomerAlreadyAvailableException` and `DockAlreadyAvailableException` one-for-one, so a client already handling lifecycle conflicts needs no new concept. The company conflict is `409` rather than the `422` that `InvalidTransportCompanyException` carries because the blocking company is stored state reached through the addressed truck, not a field the caller submitted — the same distinction `#225` used to make the not-found case `404` rather than `422`. Distinct codes are required by FR-016 and SC-006: an administrator must be able to tell "someone already reactivated this" from "the provider is archived", and the second carries a concrete remedy the first does not.

**Alternatives considered**: Reusing `InvalidTransportCompanyException` — rejected because its `422` and its message ("Transport company must exist and be available") describe a rejected payload field, which would mislead a client into highlighting a form input that does not exist on this request. One shared `E_TRUCK_LIFECYCLE_CONFLICT` — rejected because it would force the web client to parse message text to choose between two different pieces of guidance.

## Decision: Generalize the existing blockers module instead of adding a second one

**Decision**: Change `findBulkBlockers` in `apps/api/app/trucks/shared/truck_lifecycle_blockers.ts` to take an `expectedStatus: 'AVAILABLE' | 'ARCHIVED'` argument (as `customer_lifecycle_blockers.ts` already does) and extend `BulkTruckLifecycleBlocker['reason']` with `ALREADY_AVAILABLE` and `TRANSPORT_COMPANY_ARCHIVED`. A status mismatch reports `ALREADY_ARCHIVED` when `AVAILABLE` was expected and `ALREADY_AVAILABLE` when `ARCHIVED` was expected; the in-use check stays gated on `expectedStatus === 'AVAILABLE'`, and the new company check applies only when `ARCHIVED` is expected. The existing `archiveAvailableMany` call site passes `'AVAILABLE'` and keeps its current behavior.

**Rationale**: These are pure, database-free classification functions, so generalizing them is a contained, unit-testable change with a compiler-checked call site. `#225`'s research explicitly anticipated this — it recorded `ALREADY_AVAILABLE` as arriving with reactivation in `#226` — and `customer_lifecycle_blockers.ts` proves the parameterized shape works for both directions. A second module would mean two places to keep the reason vocabulary consistent, exactly the duplication Principle VI forbids.

**Alternatives considered**: A separate `truck_reactivation_blockers.ts` — rejected as splitting one vocabulary across two files. Extracting a shared site-reference classifier now that a second resource needs both directions — still rejected for the reason `#225` gave: trucks and customers disagree on both their identifying labels (`registration` versus `code` + `companyName`) and their reason vocabularies, so the abstraction would need type parameters for both and buy indirection rather than a single source of truth. Worth revisiting when a third resource needs it.

## Decision: Multiple reactivation is one transaction locking trucks then their companies

**Decision**: `LucidTruckRepository#reactivateArchivedMany` opens one transaction and: loads the submitted trucks `forUpdate()` ordered by `id`; collects the distinct `transportCompanyId` values of the ones that are `ARCHIVED`; loads those companies `forUpdate()` ordered by `id`; classifies every submitted id through `findBulkBlockers` with `expectedStatus: 'ARCHIVED'` plus the set of archived company ids; issues one guarded `UPDATE ... WHERE id IN (eligible) AND status = 'ARCHIVED'`; asserts the affected-row count equals the eligible count; and returns the reactivated trucks alongside the blockers.

**Rationale**: This is `archiveAvailableMany`'s shape with the company resolution taking the place of the usage check, so it inherits the properties `#225` established and tested: the eligible subset commits atomically (FR-027), ineligible trucks are classified before the update rather than failing it (FR-024), `reactivatedAt` / `reactivatedByUserId` / `reactivationComment` are computed once and written identically to every truck (FR-026), and the `forUpdate` locks plus the status predicate make overlapping submissions safe (FR-017). Resolving companies once for the whole submission keeps it to one bounded query rather than one per truck. Ordering both `forUpdate` queries by `id` gives the two lock classes a deterministic acquisition order, so two overlapping bulk reactivations cannot deadlock against each other.

**Alternatives considered**: Looping over `ReactivateTruckUseCase` once per selected truck — rejected because a mid-loop failure would leave an arbitrary prefix reactivated (breaking FR-027), each truck would get a different `reactivatedAt` (breaking FR-026), and it would issue one company query per truck. Refusing the whole submission when any truck is ineligible — rejected because FR-024 and both the customer and truck archive precedents require partial success. Skipping the company locks in the bulk path and relying on the single-path guarantee — rejected because the invariant is exactly as breakable in bulk as it is singly.

**Noted, not changed**: the merged `archiveAvailableMany` issues its `forUpdate()` without an explicit order, so two overlapping bulk archivals have a theoretical deadlock exposure. This slice orders its own new queries and deliberately leaves the archive path untouched — changing it is not this slice's charter, and PostgreSQL surfaces such a deadlock as a retryable error rather than a corrupt write. It is worth a follow-up issue.

## Decision: Reuse the shared lifecycle validators from their actual home

**Decision**: `reactivateTruckValidator` (`{ comment }`) and `reactivateTrucksValidator` (`{ ids, comment }`) import `lifecycleComment()` and `lifecycleIds()` from `#shared/validators/lifecycle_validator`, the same import `archiveTruckValidator` and `archiveTrucksValidator` already use.

**Rationale**: One import keeps the 1,000-character comment limit and the "at least one, no duplicates, lower-cased UUIDs" selection rule identical across every site-reference lifecycle payload, satisfying Principle VI with no new file.

**Note for reviewers**: `#225`'s research.md states these helpers live in `apps/api/app/site_references/shared/site_reference_validator.ts`. They were actually merged into `apps/api/app/shared/validators/lifecycle_validator.ts`, and no `site_reference_validator.ts` exists in the tree. This plan targets the shipped location; the stale reference in the merged `#225` research is left as-is rather than rewritten, since that artifact records what was decided at the time.

## Decision: Reactivate branch in the existing lifecycle components, with a footer for archived trucks

**Decision**: `truck-lifecycle-actions.tsx` gains the archived branch — a non-destructive button, a "Reactivate truck?" dialog, and the `reactivate` mutation — matching `features/customers/ui/lifecycle-actions.tsx`. `truck-details.tsx` renders its action footer for archived trucks as well as available ones, carrying the reactivate action alone; no edit control is offered for an archived truck, since `UpdateTruckUseCase` refuses one with `ArchivedTruckReadOnlyException`. The existing refusal handling is kept: a failed lifecycle call refreshes the truck queries before showing the error toast, so a stale view is corrected by the refusal itself (FR-019).

**Rationale**: The components, the dialog, the comment field, the toast conventions, and the administrator gate all already exist from `#225`; only the branch is missing. Rendering the footer for archived trucks is the one structural change, and it is required because the reactivate action has nowhere else to live in the details panel.

**Alternatives considered**: A separate `truck-reactivation-actions.tsx` — rejected as duplicating a dialog that differs only in labels and endpoint, which is precisely why the customer component handles both directions in one place. Offering reactivate from the directory row instead of the details panel — rejected as inconsistent with how every other lifecycle action in the workspace is reached.

## Decision: Extend selection to the archived tab rather than build a second selection model

**Decision**: In `trucks-page.tsx`, `visibleSelectedTruckIds` prunes the selection against the trucks listed in the *active* lifecycle tab instead of returning an empty set whenever the tab is not `available`; the bulk toolbar renders in both tabs for administrators and receives which direction it is acting in; `lifecycleActionIds` drops its `truckStatus === 'available'` guard so the retry path works in both directions. Switching tabs or changing the transport-company filter still prunes the selection; search still does not.

**Rationale**: `#225` restricted selection to the available tab and documented the reason in a code comment — there was no archived-tab bulk action for a pruned truck to fall back into. This slice supplies it, so the restriction is exactly the thing that must be lifted, and `customers-page.tsx` already runs the two-direction version of this model. Keeping one selection state pruned per tab, rather than two independent sets, is what makes FR-030 hold without new bookkeeping: a truck's lifecycle state determines which tab lists it, so pruning by the visible list already prevents carrying an archived truck into an archive action or an available truck into a reactivate action.

**Alternatives considered**: Separate selection state per tab — rejected as more state for no observable difference, since a truck is listed in exactly one tab. Leaving selection available-only and offering multiple reactivation from a different affordance — rejected as inventing a second selection idiom in a workspace that already has one.

## Decision: Widen the web bulk result type to cover both routes

**Decision**: `features/trucks/types.ts` keeps one `BulkTruckLifecycleResult` / `BulkTruckLifecycleBlocker` pair, sourced so that it covers both `trucks.archive_many` and `trucks.reactivate_many`, and `formatBlockerReason` in the bulk component gains labels for `ALREADY_AVAILABLE` and `TRANSPORT_COMPANY_ARCHIVED`.

**Rationale**: Both endpoints serialize the same `BulkTruckLifecycleResult` shape from the repository, so Tuyau infers the same blocker union for both — the archive route's type will advertise reason values it cannot actually return, exactly as the merged customer bulk types already do. Accepting that is cheaper than splitting the component's props into two per-direction types for a distinction no rendering path depends on: the component formats whatever reason it is given and falls back to the raw value for an unknown one.

**Alternatives considered**: Per-route blocker types with narrowed unions — rejected as requiring the shared toolbar component to be generic over its outcome type for no user-visible gain.
