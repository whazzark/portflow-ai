# Phase 1 Data Model: Correct a Customer's Product Lots at Once

No table, column, index, or seed changes (research.md Decision 11). This document describes the rows
the feature writes and reads, the command it decides on, and the web adapters.

## Persisted entities written

### Product Lot (`product_lots`, `#models/product_lot`)

| Column | Written as |
|---|---|
| `id` | Kept for corrected lots; generated by the model for added lots |
| `discharge_id` | The path discharge |
| `customer_id` | The body's `customerId`, lower-cased, for every corrected and added lot |
| `product_name` | Trimmed; temporarily the lot's own id while parked (Decision 5) |
| `expected_quantity_tonnes` | `Decimal` from the tonnage string, 3 decimals |
| `description` | Trimmed; empty becomes `null` |
| `updated_at` | Now, for corrected lots |

Constraints the write relies on:
- `product_lots_identity_unique` on `(discharge_id, customer_id, LOWER(product_name))`: checked row
  by row, hence the parking step.
- `CHECK (LENGTH(TRIM(product_name)) > 0)` and `CHECK (expected_quantity_tonnes > 0)`.
- `warehouse_door_product_lot_assignments.product_lot_id` references the lot with `RESTRICT`: the
  last resort against removing a lot with door assignments.

Lifecycle per lot in one change:

```text
listed with id ──► parked (only if its identity changes) ──► corrected
listed without id ─────────────────────────────────────────► inserted
removed ───────────────────────────────────────────────────► deleted
neither listed nor removed ────────────────────────────────► untouched (keeps its customer)
```

### Discharge (`discharges`)

`updated_at` is touched once per accepted change, as every GH-53 lot write does.

## Rows read under lock

| Read | Lock | Purpose |
|---|---|---|
| `discharges` row | `FOR UPDATE` (`lockPlannedDischarge`) | Planned status; serializes preparation writes |
| `product_lots` of the discharge (`listProductLots`) | Under the discharge lock | Ownership, identities, lot count |
| Target `customers` row (`lockCustomers`) | `FOR SHARE`, only when the group moves | Availability against a concurrent archive |
| `warehouse_door_product_lot_assignments` for removed ids (new `listLotIdsWithDoorAssignments`) | Under the discharge lock | Removal blocks, current or ended |

## Pure rules (`app/discharges/product_lots/customer_product_lots_rules.ts`)

`planCustomerProductLotsCorrection(request, lots, lotIdsWithDoorAssignments, targetCustomer)`
returns `LOT_NOT_FOUND | ISSUES | LAST_LOT | PLAN` (research.md Decision 3).

Identity key: `[customerId.toLowerCase(), productName.trim().toLowerCase()]`. This is the existing
`lotIdentityKey`, exported from `discharge_preparation_rules.ts` for reuse.

| # | Rule | Input | Outcome |
|---|---|---|---|
| R1 | Every `productLots[].id` and `removedProductLotIds[]` is a lot of the discharge with `customerId` = path customer (case-insensitive) | lots | `LOT_NOT_FOUND` |
| R2 | No id appears twice across both arrays | request | issue `productLotListedOnce` at the later position (`productLots.N.id` or `removedProductLotIds.N`) |
| R3 | Target differs from path customer ⇒ target exists and is `AVAILABLE` | targetCustomer | issue `availableCustomer` at `customerId` |
| R4 | No removed id has door assignments | lotIdsWithDoorAssignments | issue `removableProductLot` at `removedProductLotIds.N` |
| R5 | After the change, no two lots of the discharge share an identity | lots, request | issue `productLotIdentityUnique` at `productLots.N.productName` for every listed entry in a clash |
| R6 | Lots after the change ≥ 1 | lots, request | `LAST_LOT` |

- R1 is checked first, and R2 next; if R2 finds issues, the rules stop there. R3 to R5 are collected
  together. R6 applies only when there are no issues.
- `PLAN.corrections[].identityChanges` is true when a lot's identity key differs from its current
  one.
- A correction whose values are all unchanged is still planned. It writes the same values, as
  GH-53's single correction does.

Unit-test edges (`tests/unit/discharges/preparation/customer_product_lots_rules.spec.ts`):
- the swap of two names, and removal plus re-add of the same name;
- a case-only rename;
- a move onto a customer whose lot shares a name, and one without a clash;
- a clash with an unlisted lot;
- an id of another customer, and an id listed in both arrays;
- all lots removed with and without other customers;
- a door-assigned removal;
- an empty request.

## Read model

Unchanged. The response is the `DischargeDetail` of `discharges.show`.

### `customer-lots-correction.ts` (new, pure)

`correctionRowRemoval(lot | null, otherLotCount, rowCount)` returns a `LotRemovalBlock | null`:
- `E_PRODUCT_LOT_HAS_DOOR_ASSIGNMENTS` when the row's lot has door assignments;
- `E_DISCHARGE_LAST_PRODUCT_LOT` when `otherLotCount === 0 && rowCount <= 1`;
- otherwise `null`.

The web uses `LOT_REMOVAL_REASONS` for the text.

Unit-test edges:
- `__tests__/customer-product-lots-schema.test.ts`: prefill; swap accepted; clash with another customer's lot
  after a move; empty rows with and without other lots; body order and ids; field mapping.
- `__tests__/customer-lots-correction.test.ts`: every branch of `correctionRowRemoval`.
