## Delivery notes — 2026-09-11

The tasks below were run as written. They are annotated rather than rewritten, so the branch history
stays readable. Where the delivery differs:

- **T018**: the form is keyed on the session user's `id` only, not `id` and `email`. T038 foresaw
  this: keying on the address would re-seed the form when an administrator moves it, and wipe what
  the user typed. The form therefore compares against the live session address, and resets itself
  to the saved values after an accepted update.
- **T019**: `apps/web/src/routeTree.gen.ts` is gitignored and regenerated by the web `pretypecheck`
  script. There is nothing to commit.
- **The browser pass (T041) found a defect that the tests did not reproduce, and it is fixed.** In a
  real browser, the first click on **Save changes** after changing the address did nothing, and only
  a second click submitted.
  - *Cause.* Leaving the address field ran the form's blur validation while the new current-password
    field was still empty. The cross-field rule then left an error on a field the user had not
    reached yet. TanStack Form silently drops a *first* submission attempt made while the form cannot
    submit.
  - *Fix.* The rule now runs on submission only; blur judges each field on its own
    (`own-profile-form.tsx`). This is also better copy: the password is not reported missing before
    the user reaches it.
  - *Tests.* Pinned by `email.test.tsx`, "submits a confirmed address change on the first click",
    RED before the fix. `refusals.test.tsx` gains "submits again on the first click once a refused
    value is corrected".
- **Test support**: `apps/web/src/features/profile/__tests__/support.ts` holds the session fixture,
  the MSW overrides that keep `auth/me` in step with accepted updates, and the form helpers shared by
  the four test files.
- **Running the API suites in a worktree**: `apps/api/.env` is not in the repository, so the suites
  run with the variables CI sets (`.github/workflows/ci-checks.yml`, job `test-api`) together with
  `.env.test`.

## How these stories divide

One endpoint serves all five stories, so the substrate they share is Phase 2 and belongs to no story:
the shared identity rules, the exceptions, the validator, and the policy ability. The stories then
divide by behavior on that seam:

- **US1** applies a name change and shows it. It is the only phase that must ship for the feature to
  exist.
- **US2** adds the password-confirmed address change.
- **US3** proves the path is confined to oneself.
- **US4** proves what is acceptable.
- **US5** survives failure.

`update_own_profile_use_case.ts`, `update.spec.ts`, and `own-profile-form.tsx` are each
touched by several stories. Their tasks are therefore sequential across phases, never `[P]` against
each other.
