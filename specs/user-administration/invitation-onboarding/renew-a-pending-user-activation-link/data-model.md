# Data Model: Renew a Pending User Activation Link

**Feature**: [spec.md](./spec.md) · **Plan**: [plan.md](./plan.md) · **Research**:
[research.md](./research.md)

Two new columns on `users`. No new table: `user_activation_tokens`, delivered by GH-7, already holds
exactly one live link per pending user, and a renewal replaces that row.

## `users` — two new columns

| Column | Type | Null | Written by | Meaning |
|---|---|---|---|---|
| `activation_link_renewed_at` | timestamp | yes | a successful renewal | when the most recent renewal was recorded (FR-009) |
| `activation_link_renewed_by_user_id` | uuid → `users.id`, `ON DELETE SET NULL` | yes | a successful renewal | the organization admin who performed it (FR-009) |

**Invariants**

- **Event, not state** (D7): overwritten by every renewal and never cleared, not even by a later
  acceptance, so the access history keeps answering who handed out the link a person activated
  with. The same reading as `password_reset_at` / `password_reset_by_user_id`.
- **Both or neither**: the two columns are written together, by one statement, and only by the
  renewal. A renewal whose administrator is later removed keeps its date with a `null` actor, like
  every other lifecycle event.
- **No access status change** (FR-008): the renewal writes these two columns and `updated_at` only.
  `access_status`, identity, role, `invited_*`, `password`, and every other lifecycle column are
  untouched.

**Migration**: `apps/api/database/migrations/1786000000000_add_user_activation_link_renewal.ts`,
branching on dialect in both `up()` and `down()` with `disableTransactions = true` (D8).
`apps/api/database/schema.ts` is regenerated by `node ace migration:run`.

**Model**: `User` gains
`@belongsTo(() => User, { foreignKey: 'activationLinkRenewedByUserId' }) declare activationLinkRenewedBy`.
The existing `@hasOne(() => UserActivationToken) declare activationToken` gets its first reader.

## `user_activation_tokens` — unchanged schema, first replacement

| Column | Written by this feature | Value |
|---|---|---|
| `id` | yes | a new uuid: the previous row is deleted, not updated (D5) |
| `user_id` | yes | the renewed pending user; the unique index keeps one row per user |
| `hash` | yes | SHA-256 hex of the newly issued secret; the previous digest no longer exists |
| `expires_at` | yes | renewal instant + 7 days (FR-004), from `ActivationLinkIssuer` |
| `created_at` | yes | the issuance instant of *this* link |

**Invariants carried over from GH-7, now exercised**

- **One live link per pending user** (FR-003, FR-015): after a renewal, exactly one row exists for
  the user, and it holds the digest of the link just presented.
- **The previous link stops at once** (FR-003): its digest was deleted in the same transaction that
  inserted the new one, so no lookup by that digest can ever succeed again.
- **The secret is never stored** (FR-007): only the digest. The link exists in the `200` response
  and nowhere else.

## Entity mapping

| Spec entity | Where it lives |
|---|---|
| **Pending User** | a `users` row with `access_status = 'PENDING'` and no password |
| **User Activation Link** | the user's one `user_activation_tokens` row, plus the secret that exists only in the renewal response |
| **User Activation Link Renewal** | `activation_link_renewed_at` + `activation_link_renewed_by_user_id`, plus the replaced token row |
| **Organization Admin** | the actor column; the only role `UserPolicy.renewActivationLink` admits |
| **Operating Organization** | implicit, as elsewhere: one organization, one site (ADR 0003) |

## Write projections

### `RenewActivationLinkUseCase` input

```text
targetUserId: string     -- the path parameter, already validated as a UUID
actorUserId:  string     -- the authenticated organization admin
renewedAt:    DateTime   -- the controller's clock, recorded as the event date
```

### `UserRepository.renewActivationLink` command and outcome

```text
command:
  targetUserId:              string
  renewedByUserId:           string
  renewedAt:                 DateTime
  activationTokenHash:       string     -- from ActivationLinkIssuer, computed before the transaction
  activationTokenExpiresAt:  DateTime

outcome:
  { kind: 'RENEWED', user: User, activationToken: UserActivationToken }
  | { kind: 'NOT_FOUND' }
  | { kind: 'NOT_PENDING', accessStatus: UserAccessStatus }
```

The outcome is typed, not thrown. The repository owns the guarded write, and the use case picks the
refusal the caller sees. `NOT_PENDING` carries the status the row actually held, which is what the
refusal must name (FR-011).

### Use case result

```text
{ user: User, activationLink: { url: string, expiresAt: DateTime } }
```

This is the same shape as `UserInvitation`, deliberately (D10).

## Read projection — `toAdministration` gains three keys

All three are gated by `includeAccessHistory`: they are absent, not `null`, for a viewer who may not
consult the access history.

| Key | Value |
|---|---|
| `activationLinkRenewedAt` | `activation_link_renewed_at`, or `null` |
| `activationLinkRenewedBy` | the actor's `{ id, firstName, lastName }`, or `null` |
| `activationLinkExpiresAt` | the live token's `expires_at` when `access_status = 'PENDING'` and a token exists; otherwise `null` |

`preloadAccessHistory` also preloads `activationLinkRenewedBy` and `activationToken`, so every read
that serializes the history carries the three keys consistently. The transformer never reads
`activationToken.hash`.

### Web-derived state

`activationLinkState(user, now)` in `apps/web/src/features/users/helpers/activation-link.ts`:

| Condition | State |
|---|---|
| user not `PENDING`, or `activationLinkExpiresAt` key absent | `undefined` — nothing is presented |
| `activationLinkExpiresAt === null` | `'missing'` — *Not issued* |
| `activationLinkExpiresAt > now` | `'valid'` — *Valid until <date>* |
| `activationLinkExpiresAt <= now` | `'expired'` — *Expired <date>* |

## Validation rules

| Input | Rule | Refusal |
|---|---|---|
| viewer | active organization admin | `403` `E_AUTHORIZATION_FAILURE` (FR-010) |
| viewer's session | not confined to its own password renewal | `403` `E_PASSWORD_RENEWAL_REQUIRED` (existing middleware) |
| `params.id` | UUID | `422` `E_VALIDATION_ERROR` |
| target | exists | `404` `E_USER_NOT_FOUND` (FR-012) |
| target | `access_status = 'PENDING'` | `409` `E_USER_NOT_PENDING`, `meta.accessStatus` (FR-011) |

## State transition

```text
PENDING [link L₀ or none] --renew--> PENDING [link L₁, renewed_at/by]
```

The access status does not move. The only transition is the link's: L₀ stops permitting acceptance,
and L₁ starts, valid for 7 days. Every arrow out of `PENDING` — acceptance (GH-8), cancellation
(GH-12), removal (GH-14) — belongs to another slice. D6 records how those slices serialize against
this one.
