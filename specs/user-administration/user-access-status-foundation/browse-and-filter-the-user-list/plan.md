# Implementation Plan: Browse and Filter the User List

**Branch**: `feat/4-users-list` | **Date**: 2026-08-26 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from
`specs/user-administration/user-access-status-foundation/browse-and-filter-the-user-list/spec.md`

## Summary

Make the organization's users consultable, on both seams, without introducing a single write. The
API gains one endpoint — `GET /api/v1/users` — whose scope is decided from the viewer: an
organization admin reads every user with their recorded access lifecycle, an operations admin reads
active users only and without any lifecycle event, and every other role is refused. The web gains a
`/users` workbench built like the existing customers screen: access-status views with counts,
client-side search and role filter, a sortable table, and a read-only access record opened from the
collection already retrieved. No per-user endpoint, no migration, no new table.

The design decisions and their rejected alternatives are in [research.md](./research.md); the read
projections are in [data-model.md](./data-model.md); the two contracts are in
[contracts/](./contracts/).

## Technical Context

**Language/Version**: TypeScript 5.7 on Node 22, ESM throughout the PNPM/Turbo monorepo.

**Primary Dependencies**: AdonisJS 7 (Lucid, Bouncer, session auth), Tuyau for the typed API/web
contract (ADR-0005), TanStack Start + Router + Query, shadcn/Tailwind primitives, Zod for route
search-param validation.

**Storage**: PostgreSQL. The `users` table already carries every column this feature reads — GH-2
delivered them. No migration.

**Testing**: Japa for the API (`unit` and `integration` suites, SQLite-backed repository tests per
ADR-0014); Vitest + Testing Library + MSW for the web, rendering through the real router. No
`apps/web/e2e` directory exists in the repository, so this slice adds no end-to-end journey.

**Target Platform**: AdonisJS API server and a TanStack Start web application, both already deployed
from this monorepo.

**Project Type**: Web application — `apps/api` + `apps/web`.

**Performance Goals**: SC-003 — the selected view and its count within 2 seconds for a collection of
up to 200 users. One collection request, no per-user request, filtering in the client.

**Constraints**: FR-006a forbids a per-user consultation seam; FR-004 keeps the API authoritative for
authorization; FR-007 forbids exposing credentials or tokens; the `toObject()` session contract used
by `/auth/me` and `/auth/login` must not change.

**Scale/Scope**: one site, one organization, ≤ 200 users, one new endpoint, one new web route, one
new feature module, no schema change.
