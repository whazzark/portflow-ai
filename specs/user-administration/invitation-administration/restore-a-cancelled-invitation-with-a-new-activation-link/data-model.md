# Data Model: Restore a Cancelled Invitation with a New Activation Link

**Feature**: [spec.md](./spec.md) · **Plan**: [plan.md](./plan.md) · **Research**:
[research.md](./research.md)

Three new columns on `users`. No new table: `user_activation_tokens` (GH-7) already holds at most one
live link per user, GH-12 leaves a cancelled user without one, and a restoration inserts a new one.

## `users` — three new columns

| Column | Type | Null | Written by | Meaning |
|---|---|---|---|---|
| `invitation_restored_at` | timestamp | yes | a successful restoration | when the most recent restoration was recorded (FR-003) |
| `invitation_restored_by_user_id` | uuid → `users.id`, `ON DELETE SET NULL` | yes | a successful restoration | the organization admin who performed it (FR-003) |
| `invitation_restoration_comment` | text | yes | a successful restoration | their comment, trimmed; `null` when none or blank (FR-003a) |

**Invariants**

- **Latest only** (FR-003): every restoration overwrites all three columns, the comment included. A
  restoration without a comment writes `null` over an earlier restoration's comment.
- **Never cleared** (D6): no other write touches them. A later cancellation, acceptance, renewal,
  role change, or identity update leaves them as they are, so the record keeps saying who restored
  the invitation a person later activated through.
- **Written together**: the three columns change in one statement, and only on a restoration. A
  restoration whose administrator is later removed keeps its date and comment with a `null` actor,
  like every other lifecycle event.
- **Named after the invitation** (D6): `invitation_restored_*`, never `restored_*`, which would read
  as the "user restoration" `CONTEXT.md` avoids.

**Migration**: `apps/api/database/migrations/1786100000000_add_user_invitation_restoration.ts`, with
the dialect branch in both `up()` and `down()` and `disableTransactions = true`, copied from
`1786000000000_add_user_activation_link_renewal.ts` (D7). `apps/api/database/schema.ts` is
regenerated by `db:migrate`.

**Model**: `User` gains
`@belongsTo(() => User, { foreignKey: 'invitationRestoredByUserId' }) declare invitationRestoredBy`,
and `preloadAccessHistory` in `lucid_user_repository.ts` gains `.preload('invitationRestoredBy')` —
the "eighth lifecycle event is a one-line change" that function's comment anticipates.

**Factory**: `UserFactory` sets the three columns to `null` in its definition and in every state
that already nulls the cancellation pair (`active`, `passwordRenewalRequired`, `passwordReset`), so
no state inherits a stray restoration. No `restored` state is added: tests restore through the
repository, which is what they exercise.

## The one transition this feature owns

```text
CANCELLED ──restore (organization admin)──▶ PENDING
```

| Column | Before (cancelled) | After (pending again) |
|---|---|---|
| `access_status` | `CANCELLED` | `PENDING` |
| `invitation_restored_at` / `_by_user_id` / `_comment` | previous restoration or `null` | this restoration |
| `cancelled_at` / `cancelled_by_user_id` / `cancellation_comment` | the cancellation | **unchanged** (FR-002, clarification 2) |
| `invited_at` / `invited_by_user_id` | the original invitation | **unchanged** (FR-002, clarification 3) |
| `activation_link_renewed_at` / `_by_user_id` | earlier renewal or `null` | **unchanged** (FR-003) |
| `first_name`, `last_name`, `email`, `role` | as held while cancelled | **unchanged** (FR-002) |
| `password` | `null` | `null` (FR-023) |
| `updated_at` | — | the restoration instant, written by hand (guarded `.update()` bypasses the hook) |

**Every other status is refused and writes nothing** (FR-010): `PENDING`, `ACTIVE`, and
`DEACTIVATED` match the guard on no row.

## `user_activation_tokens` — unchanged schema, one row inserted

| Column | Written by this feature | Value |
|---|---|---|
| `id` | yes | a new uuid |
| `user_id` | yes | the restored user; the unique index keeps one row per user |
| `hash` | yes | SHA-256 hex of the newly issued secret, from `ActivationLinkIssuer` |
| `expires_at` | yes | issuance instant + 7 days (FR-005) |
| `created_at` | yes | the issuance instant of this link |

**Invariants**

- **No earlier link survives** (FR-006): every row for the user is deleted before the new one is
  inserted, in the same transaction. After GH-12 there is normally nothing to delete; the delete
  makes the rule unconditional (D5).
- **Exactly one live link after a restoration** (FR-004, FR-020): the row just inserted, holding the
  digest of the link presented once. A second, concurrent restoration inserts nothing.
- **Status and link together** (FR-007): the `UPDATE`, the `DELETE`, and the `INSERT` commit in one
  transaction. A failure rolls all three back: the user is still `CANCELLED` and holds no token.
- **The secret is never stored** (FR-009): only its digest. The URL exists in the use case's memory
  and in the `200` response, and nowhere else.
- **Removal takes the link with it**: `user_id` is `ON DELETE CASCADE`, so a removal that follows a
  restoration leaves no orphaned link (US5-5).

## Repository contract

`UserRepository` gains one operation, in the shape of `cancelPendingInvitation` and
`renewActivationLink`:

```ts
export type RestoreCancelledInvitationCommand = {
  id: string
  restoredByUserId: string
  restoredAt: DateTime
  /** Already normalized by the use case: trimmed, and `null` when blank. */
  comment: string | null
  /** The digest of the newly issued link, and the instant it stops being usable. */
  activationTokenHash: string
  activationTokenExpiresAt: DateTime
}

/** What the guarded write observed, never what the caller should be told. */
export type RestoreCancelledInvitationResult =
  | { kind: 'RESTORED'; user: User; activationToken: UserActivationToken }
  | { kind: 'NOT_FOUND' }
  | { kind: 'NOT_CANCELLED'; accessStatus: UserAccessStatus }

abstract restoreCancelledInvitation(
  command: RestoreCancelledInvitationCommand,
): Promise<RestoreCancelledInvitationResult>
```

`RESTORED.user` is reloaded through `preloadAccessHistory`, so every actor, the restoration's
included, and the new token's expiry are resolved for the projection.

## Use case

`RestoreUserInvitationUseCase.handle({ id, restoredByUserId, restoredAt, comment })`:

1. `ActivationLinkIssuer.issue()` → `{ url, hash, expiresAt }`, outside any transaction.
2. `restoreCancelledInvitation({ …, comment: comment?.trim() || null, activationTokenHash: hash,
   activationTokenExpiresAt: expiresAt })`.
3. `NOT_FOUND` → `UserNotFoundException`. `NOT_CANCELLED` →
   `UserNotCancelledException(accessStatus)`. `RESTORED` → `{ user, activationLink: { url,
   expiresAt } }`, the `UserInvitation` / `ActivationLinkRenewal` shape.

## Projection — `toAdministration()`

Three keys, present only when `includeAccessHistory` is true (organization admins), absent otherwise:

| Key | Type | Source |
|---|---|---|
| `invitationRestoredAt` | ISO timestamp or `null` | `invitation_restored_at` |
| `invitationRestoredBy` | `{ id, firstName, lastName }` or `null` | `invitationRestoredBy` via `toSummary` |
| `invitationRestorationComment` | string or `null` | `invitation_restoration_comment` |

`activationLinkExpiresAt` needs no change: it already reports the live token of a pending user, which
a restored user is. `toObject()` (the session representation) is unchanged.

## Web model

`UserDto` is `Route.Response<'users.index'>['data'][number]`, so the three keys arrive with the
regenerated client registry and need no hand-written type. `ActivationLinkDto` is reused as is. The
issued-link holder in `issued-activation-link.tsx` becomes
`{ user: UserDto; activationLink: ActivationLinkDto; origin: 'renewal' | 'restoration' }`.
