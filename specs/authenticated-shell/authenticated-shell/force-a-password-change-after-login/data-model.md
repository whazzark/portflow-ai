# Data Model: Force a Password Change After Login

**Feature**: `GH-117` | **Date**: 2026-08-26 | **Spec**: [spec.md](./spec.md) | **Research**: [research.md](./research.md)

## `users` table

### New column

| Column | Type | Null | Default | Notes |
|---|---|---|---|---|
| `password_renewal_required_at` | `timestamp` | yes | `NULL` | Non-null ⇒ the user must choose a new password before using the application. Set to `NULL` by a completed renewal. |

No actor column, no comment column, no check constraint, and no new `access_status` value
(research [D1](./research.md)). No foreign key, which is why the migration needs no SQLite branch
(research [D2](./research.md)).

**Existing rows** get `NULL` — correct, since no requirement has ever been recorded.

### Columns this slice writes

| Column | Written by | When |
|---|---|---|
| `password` | the renewal | on success, as a fresh scrypt hash |
| `password_renewal_required_at` | the renewal | on success, set to `NULL` |

Nothing else on `users` is touched: identity, email, role, access status, and every lifecycle
timestamp are preserved (FR-013).

### Columns this slice reads but never writes

`password_renewal_required_at` is **never set** by this slice. Recording the requirement belongs to
Reset an Active User Password (`#17`) and Reactivate a User with Fresh Credentials (`#32`) (FR-023).
Until they ship, the column is populated by the factory state and the seed fixture
(research [D12](./research.md)).

## Renewal requirement states

The requirement is one bit, orthogonal to `access_status`.

| `access_status` | `password_renewal_required_at` | Login | Reaches the application | Reaches the renewal step |
|---|---|---|---|---|
| `ACTIVE` | `NULL` | succeeds | yes | no — redirected away (FR-024) |
| `ACTIVE` | set | succeeds (FR-002) | **no** (FR-003) | yes |
| `PENDING` / `CANCELLED` / `DEACTIVATED` | `NULL` or set | refused, invalid credentials | no | no |

A non-active user never reaches the renewal step, and their requirement is left standing for a future
reactivation — the spec's edge case for a user deactivated while owing a renewal.

### Transitions

```
                          #17 password reset
                          #32 user reactivation          (not in this slice)
     no requirement ─────────────────────────────────►  requirement standing
            ▲                                                   │
            │            password renewal (this slice)          │
            └───────────────────────◄──────────────────────────-┘
```

| From | Action | Outcome |
|---|---|---|
| requirement standing | renewal with a valid password | **succeeds**: password recorded, requirement cleared, other remembered connections revoked |
| requirement standing | renewal with an invalid password | refused; password and requirement unchanged (FR-017) |
| no requirement | renewal | refused, `E_PASSWORD_RENEWAL_NOT_REQUIRED` (FR-024) |
| requirement standing | sign out | requirement stands (FR-022) |
| requirement standing | sign in again | requirement stands, renewal step presented again (FR-022) |
| requirement standing | any other request | refused, `E_PASSWORD_RENEWAL_REQUIRED` (FR-006) |

The single guarded `UPDATE` in research [D7](./research.md) is what makes the second and third rows
of that table the same mechanism: `WHERE password_renewal_required_at IS NOT NULL` matching zero rows
*is* the "no requirement" refusal, and is also what makes concurrent renewals record exactly one
password (FR-016).

## `remember_me_tokens` table

Unchanged in shape. The renewal **deletes** rows from it (FR-015).

| Rows | Fate on a successful renewal |
|---|---|
| the token presented by the renewing request | kept |
| every other token of the same user | deleted |
| every token of every other user | untouched |

With no valid `remember_web` cookie on the request, the user holds no remembered connection on this
browser and all of their tokens are deleted — the same outcome by the same rule. The one case where
the presented token cannot be identified, and all of the user's tokens including the current one are
deleted, is research [D8](./research.md); the session survives it, so the user is not signed out.

## Model and transformer

| Artifact | Change |
|---|---|
| `database/schema.ts` (`UserSchema`) | regenerated by `migration:run`; gains `passwordRenewalRequiredAt: DateTime \| null` |
| `app/models/user.ts` | no change — the column arrives through the generated schema base class |
| `UserTransformer#toObject()` | gains `passwordRenewalRequired: boolean`, derived, not picked (research [D6](./research.md)) |
| `UserTransformer#toSummary()` | no change — id and name only |

`toObject()` currently uses `this.pick(...)`, which cannot express a derived field; the boolean is
composed alongside the picked set. The raw timestamp is deliberately not serialized.

## Session representation

`GET /api/v1/auth/me` and `POST /api/v1/auth/login` both serialize with `toObject()`, so both gain the
same field. That is what lets the web shell route without a second request: `useLogin` already resets
the `auth.me` query, and the guard in `_authenticated` reads the refreshed value
(research [D11](./research.md)).
