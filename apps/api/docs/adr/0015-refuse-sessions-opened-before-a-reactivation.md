# Refuse sessions opened before a user's latest reactivation

ADR 0001 keeps the whole session in an encrypted cookie: the server holds no session record, so it has nothing it can delete to end one. `clearWithBrowser` also leaves that cookie without an expiry, so a browser that stays open keeps its session indefinitely. Until User Reactivation (GH-32) this never mattered, because the one way an administrator retires an access, User Deactivation, is enforced by `authenticateOpenSession` re-reading the user on every request and refusing anyone who is not `ACTIVE`. Reactivation breaks that assumption: the moment a deactivated user is active again, a session cookie their browser kept from before the deactivation authenticates once more, and the password renewal step it is confined to hands the choice of their new password to whoever holds that browser — without any password being presented.

Every session therefore records the reactivation it was opened under. When a session comes into being — at login, at invitation acceptance, and when the guard restores one from a remembered connection — the user's `reactivated_at` is written into it as epoch milliseconds (or left absent for a user never reactivated). `authenticateOpenSession`, the single definition of an open session, compares that value with the user's current `reactivated_at` on every request, and forgets and refuses a session whose value differs, with the same `E_UNAUTHORIZED_ACCESS` an expired remembered connection gets. The mechanics live in `app/auth/shared/session_reactivation.ts`.

The comparison is equality on the stored value, not a comparison of clocks. Both sides read the same column; a reactivation always writes a new value into it; nothing else ever writes it. A session from before the deactivation carries an earlier value or none, and is refused. A session opened after the reactivation was opened by a login that could only succeed once the reactivation had committed, so it carries the new value. A session restored from a remembered connection is stamped at restoration with the current value, which is safe because the reactivation deletes every remembered connection the user holds in its own transaction, so none that survives can predate it. A session with no value reads as a user never reactivated, so nothing changes for anyone else, and deploying the rule invalidates no legitimate session.

## Consequences

Ending a cookie-store session is now possible for exactly one trigger, and it costs no query: the user row `authenticateOpenSession` already reads carries the value compared. No migration was needed, because `reactivated_at` is already the value that changes exactly when a new period of access begins.

A test that signs in a user whose `reactivated_at` is set must open the session through `POST /api/v1/auth/login` (and replay it with `withSession(response.session())`) or prime the value with `withSession`. A bare `loginAs` puts only the user in the session, which is precisely the stale session this rule refuses.

If a second reason to end sessions ever appears — for instance, if password reset's decision to leave live sessions standing is revisited — `reactivated_at` stops being the right value to compare: it would be overloaded with events that are not reactivations. The step then is a dedicated counter column on `users`, bumped by every session-ending action and stored in the session the same way, generalizing this decision rather than adding a second mechanism beside it. Comparing a session's opening time with a stored timestamp was considered and rejected: it compares clock readings taken by different requests, possibly on different servers, and depends on the precision each dialect keeps.
