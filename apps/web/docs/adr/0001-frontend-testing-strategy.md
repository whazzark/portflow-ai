# Adopt a three-level frontend testing strategy for apps/web

`apps/web` will use three test levels — unit, feature, and e2e — rather than the four originally floated, each with a distinct job and its own tooling. Unit tests cover pure non-React logic only: adapters, mappers, and small branching business rules such as `parseApiError`. They never render anything and never exercise a hook in isolation (no `renderHook`); this level stays narrow and small in count. Feature tests are the main day-to-day coverage layer and the one TDD's red-green-refactor loop drives: one integration-style seam per feature, rendering through the real router and real providers, following the pattern already established by `auth-flow.test.tsx` during issue #115. There is no separate isolated-component-test level — testing a component like `LoginForm` on its own would duplicate feature-level coverage while coupling tests to internal boundaries that move as adapters get refactored. E2E is a full suite of complete user journeys, not a handful of smoke tests, added on top of the feature level; the duplication on critical paths is accepted, since the two layers serve different purposes — fast, fine-grained branch coverage at the feature level versus real-world fidelity at the e2e level. This mirrors `apps/api/CLAUDE.md`'s existing testing philosophy (unit for business logic, integration for the boundary contract, prefer high seams over mocking internals, don't re-prove at one level what's already covered at another), while adding a comprehensive real-browser e2e layer the backend has no equivalent of — justified by TanStack Start's SSR surface, which `apps/api` has no counterpart to.

TDD's red-green-refactor loop drives unit and feature tests only. E2E tests are written after a feature is already green at the feature level, as a safety net for what a mocked, simulated environment can't catch — SSR assembly, hydration, real network behavior — not re-driven behavior-by-behavior in strict TDD.

The feature level renders with **jsdom**, not Vitest Browser Mode. Vitest Browser Mode (via the Playwright provider) was seriously evaluated, since e2e already makes Playwright a mandatory dependency and running one engine everywhere was an attractive simplification. It was rejected because both of its original motivations eroded on inspection — the jsdom fidelity gap it was meant to sidestep (`<html>` cannot be a child of `<div>`) does not reproduce on this repo's current React 19 version, and "reuse Playwright" does not hold for an interaction layer that hangs. A benchmark found non-interactive Browser Mode tests fast (~1.5s, on par with jsdom), but every test using a locator `.fill()` or `.click()` action hung indefinitely, reproduced on two different tests. A web search confirmed the same failure class as known and open upstream in `vitest-dev/vitest` (issues #9941, #7871, #7462, #6179, discussion #7559 — checked July 2026), not a local misconfiguration: headless `locator.click()`/`.fill()` stuck in an actionability retry loop, elements reported outside the viewport despite being visible and stable, and a default `actionTimeout` frequently too low in CI or sandboxed environments. Since interactive actions are exactly what the feature level exists to drive — typing credentials, clicking submit or sign-out — this hang is disqualifying for a level meant to support a tight TDD loop, not merely an inconvenience. jsdom's risk profile is known and bounded; Browser Mode's is not, and chasing a fix carries real cost with no guaranteed payoff for a tool whose original selling points were already weak. This is revisitable if the upstream issue is fixed and ecosystem signal improves. Playwright Component Testing and Storybook's test runner were also considered and rejected on tool-fit grounds, independent of the hang.

The feature level's network-mocking strategy is **MSW** (`msw/node`, `setupServer`), ratifying the pattern already built during issue #115 — no change to `apps/web/src/test/msw/*` or `apps/web/src/test/setup.ts` was required by this decision. Mocking earns its place at this level for two reasons the real-API e2e level cannot structurally cover, not as redundant safety on top of e2e: TDD-loop speed, since e2e boots a real `apps/api` instance against a real database and is too slow to run on every save; and failure isolation, since a failing mocked test points at frontend logic specifically rather than "somewhere in the stack," and some states — a genuine network failure surfaced as `HttpResponse.error()` → `TuyauNetworkError` — are close to impossible to reproduce deterministically against a real backend while trivial to declare with MSW. Mocking the Tuyau client module directly and a hand-rolled `ky`/fetch mock were both considered and rejected: the former bypasses Tuyau's real request-building and error-wrapping code with compounding drift risk as the API grows, and the latter intercepts at the same point as MSW for strictly more manual work. Neither Tuyau's own documentation nor `ky`'s own README recommends either alternative over MSW.

The e2e level uses **Playwright Test**, run against a real `apps/api` instance and a real database — never MSW — since a mocked e2e level would only duplicate the feature level with added latency while validating nothing extra: real session cookies, CORS, and real error-response shapes are exactly what this level exists to catch. Playwright was chosen over Cypress because its `webServer` config accepts multiple entries natively, mapping directly onto booting both `apps/web` and `apps/api` (against a real database) together with teardown; because it ships free, built-in CI sharding via `--shard`, unlike Cypress's Cloud-account-gated parallelism; because TanStack itself dogfoods only Playwright across its Start example apps; and because `@playwright/test` was already present transitively in `pnpm-lock.yaml` at the exact `latest` version, with Chromium binaries already cached locally, making it the lowest-friction adoption path of the two tools evaluated.

The e2e suite runs in CI as a **decoupled job**, on the same triggers as `ci-checks.yml` (`pull_request`, `push` to `master`, `workflow_call`) — not folded into the existing `checks` job, which would add e2e's full latency to every PR's feedback loop serially, and not scheduled or gated, which would weaken the intent that e2e act as a safety net running before every deploy. It lives in its own workflow file, `.github/workflows/e2e.yml`, with its own job declaring a scoped `services: postgres:` container reachable via `localhost:5432` and torn down automatically when the job ends, following the standard GitHub Actions pattern for provisioning a database service; this keeps `ci-checks.yml` a fast, simple lint/typecheck/unit-and-feature-test file, while the heavier e2e job — Postgres service, browser install, multi-service boot — lives on its own. `apps/api`'s own test suite runs on in-memory SQLite in CI today, not Postgres, so this is new infrastructure for the repo, not a port of an existing pattern. `e2e.yml` duplicates `ci-checks.yml`'s `on:` triggers rather than inheriting them, since sibling workflow files do not share trigger configuration; and `cd-production.yml`'s `build` job depends on both `verify` (the existing `ci-checks.yml` reuse) and a new `e2e` job reusing `e2e.yml`, so a production release cannot ship without both passing.

The e2e suite is invoked through a dedicated `pnpm e2e` script and a matching `e2e` turbo task, deliberately kept separate from `pnpm test` and the existing `test` turbo task. Turbo dispatches tasks by script name across workspace packages, which is exactly what lets `apps/web`'s Vitest suite join `pnpm test` automatically today with no extra wiring — the same mechanism would make e2e block every PR and every production release if it were named into a `test` script, since `ci-checks.yml`'s `pull_request` trigger has no path filtering and `cd-production.yml` reuses `ci-checks.yml` wholesale as its `verify` job. Naming the e2e suite `e2e` instead keeps it locally runnable (`pnpm e2e`) and consistent in shape with the rest of the pipeline, without accidentally coupling it to the fast unit-and-feature-test gate.

Visual regression and automated accessibility (a11y) testing are out of scope for this decision; both were ruled out while naming the destination and may become a separate future effort if they turn out to be needed.
